# 决策记录

按时间顺序记录「为什么这样做」。每条只保留仍然生效的结论。

---

## D1 · 帧保存完整舞台快照，而不是增量补丁

**背景**：v1 的帧用 `null` 表示「本帧不改变该属性」，非 null 才覆盖。读剧本时无法判断当前背景是什么，必须从前往后脑补；一旦漏字段就黑屏。

**决定**：每帧完整记录 `bg` / `bgm` / `cast`，播放器不做合并。新建帧时编辑器用上一句台词的舞台预填。

**代价**：JSON 体积变大（一部 500 帧的作品约几百 KB，压缩后可以忽略）；改背景要逐帧改（实际上这符合"分镜"的心智模型）。

**收益**：帧可独立阅读、独立复制、独立撤销；播放器无状态可猜。

---

## D2 · 编辑器预览与导出作品共用同一份运行时

**背景**：两套渲染代码必然走样。

**决定**：运行时只写一份（`public/engine/runtime.js`），编辑器通过 iframe 加载它，导出时原样打包。

**代价**：运行时必须是 classic script（不能用 ESM 被 Vite 打包），也不能 import 编辑器里的 TS 类型。用 `RuntimePayload` 接口在 TS 侧做结构对齐，并由 `vp check` 的 `ignorePatterns` 放行该目录。

**收益**：所见即所得是**结构上**保证的，而不是靠人肉同步。

---

## D3 · 剧本数据以 `data.js` 注入，而不是 `fetch('data.json')`

**背景**：交付要求是「解压后双击 `start.html` 就能玩」，也就是 `file://` 协议。Chrome 会以 CORS 为由拒绝 `file://` 的 `fetch`，ES module 同理。

**决定**：导出 `data.js`（`window.GALASTAR_DATA = {...}`）用 `<script src>` 加载；运行时是 IIFE classic script；素材用相对路径 `<img src>` / `<audio src>`。

**收益**：零服务器、零安装，双击即玩。

---

## D4 · 素材二进制放 IndexedDB，不放 localStorage

**背景**：localStorage 只有 5MB，且只能存字符串（base64 会再膨胀 33%）。

**决定**：作品 JSON 与素材 Blob 都进 IndexedDB，素材键 `${projectId}:${assetId}`。

**代价**：数据只在本机、本浏览器；需要显式的「导出工程备份」来迁移。这一点在 UI 和 README 里都明说了。

---

## D5 · 撤销用整份快照，不用命令模式

**背景**：编辑器有 ~20 种变更入口（改台词、换背景、调站位、增删帧、改角色、删素材…）。命令模式要为每个入口写一对 do/undo，且容易写漏。

**决定**：`mutate(recipe)` 统一入口：`structuredClone` 当前作品 → 改 → 压栈。

**代价**：单步内存开销 = 一份作品 JSON（几十 KB 到几 MB）。

**收益**：新功能不需要额外写撤销逻辑，永远不会出现「某操作不可撤销」的漏洞。上限 80 步兜底。

---

## D6 · 没有服务端，也不做账号

**决定**：纯前端 SPA，部署到任意静态托管。没有登录、没有云同步、没有协作。

**理由**：核心交付物（可玩的作品包）本身就必须离线可运行；引入服务端只会增加成本，而不改变产物。云同步是明确的范围外需求，未来如需要，应当作为独立能力（导出/导入已提供基础）。

---

## D7 · 打包素材保持原格式、原文件名

**决定**：不上传时转码，不重命名（仅按 `bg-` / `sprite-` / `bgm-` / `voice-` / `sfx-` 前缀统一命名并去重）。

**理由**：转码需要 WebCodecs/wasm，体积和复杂度都不划算；保持原名让用户在 `media/` 里能直接替换文件。体积控制交给用户（README 里给了建议）。

---

## D8 · 包管理器固定 pnpm，Node 固定 24

**决定**：`.nvmrc` 写 `24`；依赖只用 pnpm（提交 `pnpm-lock.yaml`，不放 `package-lock.json`）；安装策略写在 `pnpm-workspace.yaml` 的 `nodeLinker: hoisted`。

**为什么是 hoisted**：pnpm 默认的 isolated 布局靠符号链接把直接依赖挂到 `node_modules` 根下。本机（Windows、未开启开发者模式）实测两次都是「安装成功但顶层什么都没有」——`.pnpm` 里有包、`.bin` 里有可执行文件，但 `node_modules/react`、`node_modules/typescript` 不存在，`tsc` 直接 `MODULE_NOT_FOUND`。改成平铺布局后一次通过。

**踩过的坑**：pnpm 12 起 `nodeLinker` 只在 `pnpm-workspace.yaml` 里生效，写在 `.npmrc` 里会被静默忽略（`pnpm config get node-linker` 返回 `undefined`，`.modules.yaml` 里仍是 `isolated`）。

**代价**：平铺不省磁盘；换来的是「换任何一台机器，`pnpm install` 都能直接跑」。

**CI**：`setup-vp` 显式传 `package-manager: pnpm`，并加一步 `Verify package manager` 校验 `node_modules/.modules.yaml` 存在——这个文件只有 pnpm 会写，能防止哪天悄悄退回别的包管理器。

---

## D9 · 帧的四种类型固定，不提供脚本语言

**决定**：`line` / `choice` / `jump` / `end`，分支通过「目标场景 + 标记条件」表达。

**理由**：v1 用 `eval()` 执行选项里的 JS 字符串——这既是安全问题，也让剧本无法被可视化编辑和校验。声明式结构可以被检视器完整覆盖，条件强度（标记 + 六种比较）已经够表达常见分歧与好感度门槛。

---

## D10 · 编辑器只做桌面宽屏

**决定**：三栏布局（276 / 自适应 / 372），最小可用宽度约 1180px，不做移动端适配。

**理由**：Galgame 创作是重键盘、重预览的长时段工作；把三栏硬塞进手机只会两边都难用。播放器（导出产物）对移动端是适配的。

---

## D11 · 播放器默认皮肤是 PGF

**决定**：`meta.theme.skin` 取值 `pgf | night`，新建作品默认 `pgf`。皮肤只靠根节点的 `data-theme` 切换，编辑器预览与导出产物共用同一份 `runtime.css`。

**理由**：PGF 是初代原型里手写的那套界面（照着 NEKOPARA 的排版做的）：台词不上对话框、白字配暗红描边直接压在画面上、画面本身糊 4px、说话的人亮着其他人压暗、系统菜单藏在右下角几乎看不见、选项是一根暗红横条、选中时先闪白再沉黑。它比通用暗色 UI 更像「一部日式 Galgame」，所以定为默认而不是可选。

**做法**：PGF 是基础样式，`night` 只覆盖「材质 + 位置」约 150 行，不重复整套骨架。`accent` 在 night 里驱动按钮与高亮；pgf 里名字固定暖橙（保留原版识别度），角色色只用于记录面板。

**代价**：两套皮肤共用一套 DOM 与 class，任何结构性改动都要在两边各看一眼——接受，因为导出产物只带一个 CSS 文件，玩家那边零成本。

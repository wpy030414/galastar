# 决策记录

按时间顺序记录「为什么这样做」。每条只保留仍然生效的结论。

---

## D1 · 帧保存完整舞台快照，而不是增量补丁

**背景**：v1 的帧用 `null` 表示「本帧不改变该属性」，非 null 才覆盖。读剧本时无法判断当前背景是什么，必须从前往后脑补；一旦漏字段就黑屏。

**决定**：每帧完整记录 `bg` / `bgm` / `cast`，播放器不做合并。新建帧时编辑器用上一句台词的舞台预填。

**代价**：JSON 体积变大（一部 500 帧的作品约几百 KB，压缩后可以忽略）；改背景要逐帧改（实际上这符合"分镜"的心智模型）。

**收益**：帧可独立阅读、独立复制、独立撤销；播放器无状态可猜。

---

## D2 · 编辑器预览与导出作品共用同一份运行时

**背景**：两套渲染代码必然走样。

**决定**：运行时只写一份（`public/engine/runtime.js`），编辑器通过 iframe 加载它，导出时原样打包。

**代价**：运行时必须是 classic script（不能用 ESM 被 Vite 打包），也不能 import 编辑器里的 TS 类型。用 `RuntimePayload` 接口在 TS 侧做结构对齐，并由 `vp check` 的 `ignorePatterns` 放行该目录。

**收益**：所见即所得是**结构上**保证的，而不是靠人肉同步。

---

## D3 · 剧本数据以 `data.js` 注入，而不是 `fetch('data.json')`

**背景**：交付要求是「解压后双击 `start.html` 就能玩」，也就是 `file://` 协议。Chrome 会以 CORS 为由拒绝 `file://` 的 `fetch`，ES module 同理。

**决定**：导出 `data.js`（`window.GALASTAR_DATA = {...}`）用 `<script src>` 加载；运行时是 IIFE classic script；素材用相对路径 `<img src>` / `<audio src>`。

**收益**：零服务器、零安装，双击即玩。

---

## D4 · 素材二进制放 IndexedDB，不放 localStorage

**背景**：localStorage 只有 5MB，且只能存字符串（base64 会再膨胀 33%）。

**决定**：作品 JSON 与素材 Blob 都进 IndexedDB，素材键 `${projectId}:${assetId}`。

**代价**：数据只在本机、本浏览器；需要显式的「导出工程备份」来迁移。这一点在 UI 和 README 里都明说了。

---

## D5 · 撤销用整份快照，不用命令模式

**背景**：编辑器有 ~20 种变更入口（改台词、换背景、调站位、增删帧、改角色、删素材…）。命令模式要为每个入口写一对 do/undo，且容易写漏。

**决定**：`mutate(recipe)` 统一入口：`structuredClone` 当前作品 → 改 → 压栈。

**代价**：单步内存开销 = 一份作品 JSON（几十 KB 到几 MB）。

**收益**：新功能不需要额外写撤销逻辑，永远不会出现「某操作不可撤销」的漏洞。上限 80 步兜底。

---

## D6 · 没有服务端，也不做账号

**决定**：纯前端 SPA，部署到任意静态托管。没有登录、没有云同步、没有协作。

**理由**：核心交付物（可玩的作品包）本身就必须离线可运行；引入服务端只会增加成本，而不改变产物。云同步是明确的范围外需求，未来如需要，应当作为独立能力（导出/导入已提供基础）。

---

## D7 · 打包素材保持原格式、原文件名

**决定**：不上传时转码，不重命名（仅按 `bg-` / `sprite-` / `bgm-` / `voice-` / `sfx-` 前缀统一命名并去重）。

**理由**：转码需要 WebCodecs/wasm，体积和复杂度都不划算；保持原名让用户在 `media/` 里能直接替换文件。体积控制交给用户（README 里给了建议）。

---

## D8 · 包管理器固定 pnpm，Node 固定 24

**决定**：`.nvmrc` 写 `24`；依赖只用 pnpm（提交 `pnpm-lock.yaml`，不放 `package-lock.json`）；安装策略写在 `pnpm-workspace.yaml` 的 `nodeLinker: hoisted`。

**为什么是 hoisted**：pnpm 默认的 isolated 布局靠符号链接把直接依赖挂到 `node_modules` 根下。本机（Windows、未开启开发者模式）实测两次都是「安装成功但顶层什么都没有」——`.pnpm` 里有包、`.bin` 里有可执行文件，但 `node_modules/react`、`node_modules/typescript` 不存在，`tsc` 直接 `MODULE_NOT_FOUND`。改成平铺布局后一次通过。

**踩过的坑**：pnpm 12 起 `nodeLinker` 只在 `pnpm-workspace.yaml` 里生效，写在 `.npmrc` 里会被静默忽略（`pnpm config get node-linker` 返回 `undefined`，`.modules.yaml` 里仍是 `isolated`）。

**代价**：平铺不省磁盘；换来的是「换任何一台机器，`pnpm install` 都能直接跑」。

**CI**：`setup-vp` 显式传 `package-manager: pnpm`，并加一步 `Verify package manager` 校验 `node_modules/.modules.yaml` 存在——这个文件只有 pnpm 会写，能防止哪天悄悄退回别的包管理器。

---

## D9 · 帧的四种类型固定，不提供脚本语言

**决定**：`line` / `choice` / `jump` / `end`，分支通过「目标场景 + 标记条件」表达。

**理由**：v1 用 `eval()` 执行选项里的 JS 字符串——这既是安全问题，也让剧本无法被可视化编辑和校验。声明式结构可以被检视器完整覆盖，条件强度（标记 + 六种比较）已经够表达常见分歧与好感度门槛。

---

## D10 · 编辑器只做桌面宽屏

**决定**：三栏布局（276 / 自适应 / 372），最小可用宽度约 1180px，不做移动端适配。

**理由**：GalGame 创作是重键盘、重预览的长时段工作；把三栏硬塞进手机只会两边都难用。播放器（导出产物）对移动端是适配的。

---

## D11 · 播放器默认皮肤是 PGF

**决定**：`meta.theme.skin` 取值 `pgf | night`，新建作品默认 `pgf`。皮肤只靠根节点的 `data-theme` 切换，编辑器预览与导出产物共用同一份 `runtime.css`。

**理由**：PGF 是初代原型里手写的那套界面（照着 NEKOPARA 的排版做的）：台词不上对话框、白字配暗红描边直接压在画面上、背景原样清晰、说话的人亮着其他人压暗、系统菜单藏在右下角几乎看不见、选项是一根暗红横条、选中时先闪白再沉黑。它比通用暗色 UI 更像「一部日式 GalGame」，所以定为默认而不是可选。

**做法**：PGF 是基础样式，`night` 只覆盖「材质 + 位置」，不重复整套骨架。两套皮肤的背景都不做模糊。`night` 的差异集中在台词区：画面上下各压一层「黑 → 透明」渐变遮罩（上 104px、下 214px，曲线按参考画面量出来的），台词不上底板，左下灰字说人名、右侧白字说台词，两栏共一条基线（名字 240px 定宽，说话人有无都不让台词左右跳）。`accent` 在 night 里只落在人名左边那根 3px 细 bar 上（角色自带颜色优先），外加按钮与高亮；pgf 里名字固定暖橙（保留原版识别度），角色色只用于记录面板。

**为什么名字变灰**：主题色原本染在人名上，字号一小、颜色一淡就糊成一团；改成「人名恒灰 + 左侧色条」后，颜色成了信息（谁的台词），字本身只负责读。

**代价**：两套皮肤共用一套 DOM 与 class，任何结构性改动都要在两边各看一眼——接受，因为导出产物只带一个 CSS 文件，玩家那边零成本。

## D12 · 立绘摆放记在帧上，而不是记在角色上

**背景**：立绘原图往往不规矩。同一个角色的几张表情可能各自裁切不同、透明留白多少不一，三个固定站位（左 3% / 居中 / 右 3%）没法让它们看起来一样大、站在同一条地平线上。

**决定**：`cast.***.transform = { scale, offsetX, offsetY }`，写在**帧**上，随帧快照一起继承；单位为站位高度百分比与舞台像素（1280×720 坐标系，播放器缩放时跟着舞台一起缩）。缩放原点固定在脚底中点，放大时人物仍站在原来的地上。

**为什么不放在角色或素材上**：摆放同时取决于「哪张图」和「这一帧里她站在谁旁边、要多大存在感」，是演出决定，不是素材属性。同一张立绘在特写帧要放大压满，在远景帧要缩小让位——放在角色上就退化成「一张图只能有一种用法」，也和 D1 的帧快照模型冲突。

**继承规则**：新建帧逐槽位深拷贝上一帧的摆放（同角色换表情也保留——同一画布的偏移可复用）；**槽位换人则清零**，否则上一个角色的留白量会错加到新角色身上。

**代价**：改一张图的整体观感要逐帧调。缓解办法是「新建帧即继承」——绝大多数连续台词帧本来就沿用同一个摆法，只有真正的演出变化才需要动手。

**兼容**：旧作品没有该字段。`db.ts` 的 `hydrate()` 在读取入口补 `100 / 0 / 0`；播放器 `readTransform()` 独立兜底并夹取到合法范围，因为导出的 `data.js` 是手工可改的外部输入，脏值（NaN、越界）不能让立绘凭空消失。

## D13 · 播放器工具栏只有 自动 / 记录 / 存档 / 设置

**决定**：右下角的系统菜单固定四项，**不提供「全屏」按钮，也不提供「跳过」按钮**。全屏仍有两条通路：设置面板里的「切换全屏」按钮，以及 `F` 键；快进仍有 `Ctrl`（按住）与 `A`（自动播放）。

**理由**：全屏在设置面板里已经存在，工具栏再放一个是同一功能的两个入口，而这块菜单的设计前提是「几乎看不见、鼠标过去才浮出来」，多一项就多一分存在感。「跳过」更是要刻意去掉的：它把「作者排好的一句一句」变成一个可以瞬间冲到底的动作，等于在界面上承认「这段可以不看」——对做演出的人是种冒犯。快进留在键盘上，是给需要的人的后门，而不是摆在脸上的推荐。

**代价**：触屏玩家（没有 `Ctrl` / `F`）拿不到快进与全屏。缓解是移动端浏览器可用系统自带的全屏手势；若日后要补，应该在设置面板里加开关，而不是把按钮放回工具栏。

**实现**：`tools` 数组只有四项，`syncToolButtons()` 随之简化为只管 `auto` 的高亮；`view.skip` 状态机（`applySkipState` / `fastForward` / `gs-skipping`）原样保留，因为 `Ctrl` 快进依赖它。

---

## D14 · 编辑器语言与作品语言分开，主题走 CSS 变量

**决定**：编辑器的界面语言与主题存在 `localStorage`（`galastar.prefs`），只作用于编辑器；作品给玩家看的语言写进 `project.meta.locale`，随 `data.js` 一起导出。主题不写第二套样式表，而是在 `:root` 定义深色、`.light` 覆盖同名变量。

**理由**：用中文工作、发布英文作品是常态。把两者绑在一起，会让「把编辑器切到英文」意外改写已经发布作品的玩家界面；反过来，作品换语言也不该把作者的工作台一起翻过去。主题同理：PGF / 夜航是作品的皮肤，明暗只是工作台。

**代价**：一个页面里同时存在两种语言的可能性（英文编辑器里放中文作品标题）——这是数据与界面的正常分界，不是缺陷。

**兼容**：旧作品没有 `meta.locale`，导入时归一化为 `zh-CN`；播放器在字段缺失时才回退到浏览器语言。

**实现**：`prefs.tsx` 在 `main.tsx` 里先于首帧应用，避免深色闪一下；`translate()` 是纯函数，`lib/` 也能用；运行时不能 import 词典，自带 `STRINGS` 表并用 `data-i18n` 节点在语言变化时整批刷新。

## D15 · CLI 复用 TS 源码运行，打包核心与浏览器共享

**决定**：新增 `bin/galastar`，命令本体是 TypeScript，由 `bin/galastar.mjs` 注册
`module.registerHooks`（`@/` 别名 + 无扩展名补 `.ts`）后交给 Node 原生类型擦除执行；
打包的核心逻辑抽到 `src/lib/pack-core.ts`，浏览器与 CLI 各自只做「取播放器、取素材、写字节」。

**理由**：CLI 一旦自带一份工程 schema 与打包模板，就会和编辑器缓慢分叉——两边都能跑，
产物却不一样。把 `pack-core` 做成纯函数、把环境差异压到两个薄适配层，
才能保证「GUI 导出的包」与「终端打的包」长期一致。相比引入 `tsx`、tsup 或 vite lib 构建，
解析钩子只有三十行、零依赖，且能让 `pnpm link --global` 直接可用。

**代价**：CLI 依赖 Node 的类型擦除能力，最低版本抬到 24；CLI 导入链不能用 `.tsx`、
`enum`、`namespace`；tsconfig 的 `include` 要加上 `bin`，`vp check` 才会覆盖它。
解析规则集中在一个文件，将来若换成打包器，只需替换启动器。

**实现**：`pure.ts` 收纳 `uid` / `safeFileName`，`asset-names.ts` 收纳素材命名，
让 CLI 的导入链不经过 `utils.ts`（那里拉着 clsx / tailwind-merge）。
CJS 依赖的 `require` 在钩子里显式放行，避免把 jszip 内部路径改写成 `file://`。

## D16 · Agent 的输入只要 project.json，不引入剧本 DSL

**决定**：CLI 只接受 `project.json`（或含它的 `.galastar` 工程包），不设计
`@scene` / `角色：台词` 之类的剧本文本格式，也不做「DSL → JSON」编译。

**理由**：`Project` 的结构已经是完整的舞台快照模型，编辑器的每一项操作都能落到它上面。
再加一层 DSL，就要维护语法、错误定位、双向转换，以及「DSL 表达不了、只能手改 JSON」
的裂缝；而这些成本最终都会变成 Agent 的调试负担。对 Agent 而言，结构化的 JSON 加上
稳定的错误码，比一门只有本项目会用的新语言更好用。

**代价**：手写长剧本时 JSON 更啰嗦，`cast` / `bg` 这些快照字段要重复写。
缓解是 `init --template demo` 给一份可复制的最小工程，`validate` 逐条指出重复 id、
悬空 target、死锁选项，`assets` 由 `asset add` 代管文件名与 id。

**实现**：`.claude/skills/galastar/references/project-json.md` 是字段事实来源；
`docs/specs/galastar-cli.md` 是命令契约；两者与 `src/lib/types.ts` 一起改。

## D17 · 远程素材只存 URL，不复制字节

**背景**：素材常常已经托管在 CDN / 图床上。作者想直接引用，而不是把几 MB 的图片再复制进工程目录和每一份导出包。

**决定**：`AssetRecord` 增加可选的 `url`。填了 `http(s)` 链接的素材视为远程：不读 IndexedDB、不要求 `assets/` 下有文件、打包时不写 `media/`，`data.js` 里 `assets[id].path` 直接使用该 URL。只接受 `http://` / `https://`；`data:` / `file:` / `javascript:` 在导入、CLI 与校验器三处都会被拒绝。

**理由**：引用与分发是两件事。素材放在作者可控的托管上时，工程应该能表达「它在那里」，而不是强迫复制一份。打包器只负责把本地字节搬进 zip；远程素材的可用性是作者与托管方的责任。把这条边界写进数据模型，比在打包器里偷偷下载更可预期。

**代价**：导出的作品不再保证离线——链接失效、跨域策略变化、托管方限流都会让画面空掉。校验器只能验协议与引用，不能验证可达性；只有 `shot` / `serve` 真的加载时才会暴露 404。默认建议仍是本地素材，远程是显式选项。

**实现**：`isHttpUrl` 是唯一的协议判定，`loadAssetUrls`、`pack-core.assetRuntimePath`、`validate.ts` 与 CLI 都复用它。远程素材仍保留唯一的 `fileName`，方便以后改回本地文件而不动引用；`validate` 对远程素材跳过本地文件检查，`build` 也不会把它计入缺失。

## D18 · 新作品默认落在 ~/Documents/GalastarWorks

**背景**：Agent 需要一个稳定、可预期的作品落点。默认建在当前目录，会让工程散落在仓库、临时目录或任意 cwd 里；产物也会跟着跑，很难在下次会话里找回。

**决定**：`init` 的裸名字解析为 `~/Documents/GalastarWorks/<proj_name>`；不给位置参数时用 `--name`（缺失则 `untitled`）。带 `/` 或 `\` 的路径按相对/绝对路径理解，工作区优先级为 `--workspace` > `GALASTAR_WORKSPACE` > 默认位置。`doctor` 输出工作区根与是否存在。

**理由**：作品数据与工具仓库应该分开。工作区固定后，`dist/`、`.galastar/` 的落点也随之确定，既不污染 Galastar 仓库，也不需要每次复述绝对路径；显式路径仍然保留，方便把某部作品放进它自己的版本库。

**代价**：默认行为从「当前目录」变成「工作区」。已有脚本若依赖 cwd，需要显式写 `./name`。Windows 的 `Documents` 可能被 OneDrive 重定向，实际位置以 `galastar doctor` 为准。

**实现**：`resolveWorkspaceRoot()` 负责优先级与 `~` 展开；`init` 用 `safeFileName` 归一化目录名，`scaffoldProject` 递归创建父目录；`--json` 的 `data.dir` 是最终绝对路径，`data.workspace` 是工作区根。

## D19 · 幕间过渡用「点任意处 + 幕名卡」，不再给按钮菜单

**背景**：幕末卡曾经给出「继续 / 回到标题 / 再来一次」三个按钮。它把一次换幕做成了一个迷你标题界面：玩家的手指本来在画面上，却要先去找按钮；而且「回到标题」「再来一次」出现在每一幕结尾，等于在故事中途反复劝人退出。

**决定**：`end.next` 指向下一幕时，幕末卡不渲染任何按钮，整张卡就是「继续」；点击任意处后，幕末卡淡出、下一幕的幕名开场帧淡入（交叉渐变），再点一下才进入第一句。只有全线终点（`next` 为 `null`）保留「回到标题」，并取消「再来一次」。

**代价**：多了两次主动点击才能读到下一幕第一句；幕名卡是运行时合成的帧，不落在 `project.json` 里，作者无法逐帧调整它的版式。

**收益**：换幕不再打断「点击画面」这一个动作；每幕有一个专属的开场停顿，幕名本身成为演出的一部分；终点与幕间的语义彻底分开。

**实现**：`leaveAct()` / `dismissOpening()` / `releaseHeld()`；幕名卡用 `hold` 模式先把新幕的背景、立绘、音乐与说话人摆好，卡片退场后才开始逐字。换幕时显式恢复 `view.running`，修掉「跨幕后点不动」的致命回归。

## D20 · 台词记录按幕隔离

**背景**：回看面板一直展示从开局到现在的全部台词。第一幕过半后，记录已经长得失去意义；它也让存档体积随游玩时长无上限增长。

**决定**：`view.history` 只保留当前场景（幕）的台词，换幕第一句会清空上一幕的记录；存档写入 `historyScene`，读档时场景不符的记录直接丢弃。

**代价**：玩家无法回看上一幕说过的话；跨幕后的回看是「从这一幕开头到现在」。

**收益**：记录面板始终是一幕的篇幅，读起来像分镜脚本而不是聊天记录；`historyScene` 让旧存档也能安全降级。

**实现**：`pushHistory()` 在 `view.historyScene !== view.sceneId` 时重置；`writeSave` / `loadSlot` 同步 `historyScene`。

## D21 · 心理活动用「归因有无」区分两种台光，不另设模式

**背景**：视觉小说里有两类「不是声音」的台词——场上某个人的内心独白，以及第一人称「我」的想法。两者在排版上一样（都不该出现名牌），在演出上却相反：前者说话的人还在台上，必须继续亮着他；后者没有任何人开口，全部立绘都该压暗。如果做成「独白 / 旁白」两个开关，作者要同时判断「这句话归谁」和「亮不亮人」，两个旋钮互相牵制，还容易和已有的说话人下拉框打架。

**决定**：只加一个布尔 `innerVoice`，语义是「这句是想法，不是声音」，默认关。它负责隐掉名字牌；台光不新增字段，直接复用 `speaker.characterId` 这个既有事实——归因到某个角色就只亮他一个，归因是空的（旁白位、或自定义名）就全场压暗。回看记录继续记归因，所以「谁在想」在读记录时仍然可查，只是当下不显示。

**代价**：「用自定义名写第一人称」的作者会得到全场压暗而不是亮某人，这层语义要靠界面上那句提示讲清楚，字段本身不自明；旧工程缺 `innerVoice` 时按 `undefined` 假处理，等价于关。

**收益**：一个开关覆盖两种情况，判据是模型里已有的信息，不需要新增第三态；亮暗与名牌互不干扰，改皮肤或改归因都不会意外改变另一件。

**实现**：`runtime.js` 的 `render()` 用 `displayName && !frame.innerVoice` 决定名字牌；`applyCast()` 里 `allDim = innerVoice && !speakerId`，`gs-slot-speaker` 取反、`gs-slot-dim` 加宽。编辑器说话人下拉框右侧是一个虚线气泡图标按钮（开启后点亮为 star 色），下方按归因给出两种解释文案。
